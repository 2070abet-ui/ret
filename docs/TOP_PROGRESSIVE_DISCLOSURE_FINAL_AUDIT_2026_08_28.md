## 1. 必須確認（10項目）

Playwright（本番URL `https://ret4853.2070abe.workers.dev/`、PC 1440×900・モバイル375×812）と既存コード（`tools/sitegen/templates.py`）を確認した結果。

### 1. 初期6枚／4枚という件数は妥当か → **妥当**

- PC：`.service-grid`は3列固定（900px以上）。**6枚は2行×3列でちょうど割り切れ、行の途中で切れる不自然さがない**（実装後の見た目が崩れない）。
- モバイル：実測で1〜4枚目の高さ合計は913px（1226px→2139px）＝**モバイル1画面（812px）の約1.1倍**。「もう一声スクロールすれば見える」という自然な単位になっている。6枚では1226px→2648px＝1422px（1.75画面）とやや長くなる。
- Web調査（前回分）の一致した知見「レコメンドは3〜4件」「Amazonは画面サイズに応じ4〜7件」と照らすと、**画面が狭いモバイルほど下限（4）、余裕のあるPCは中間〜上限（6）**という配分は妥当な根拠づけができる。

### 2. 「残りを見る」の位置・文言・UIは自然か → **自然にできる（設計を以下のとおり具体化）**

- 位置：初期表示グリッドの直下、キャンペーンセクションの手前。
- 文言：診断ツールの結果画面に既に存在する「他にも◯件が条件に一致しています→比較一覧で全件見る」という既存の言い回し（`build_diagnosis_tool()`内、変更対象外）と**トーンを合わせ**、「残り9社をすべて見る ▾」とする。誇張・煽り文言は使わない。
- UI：後述のとおり`.text-link`／FAQアコーディオン（`.faq-item summary`）と同系統の控えめな見た目にし、`.btn-primary`（詳しく見る等の実CTA）とは明確に区別する。

### 3. 展開前後で視覚階層が崩れないか → **崩れない**

展開後に表示される7〜15番目のカードは、1〜6番目と**全く同じ`.svc-card-top`クラス・同じ`.service-grid`（別インスタンスだが同一CSS）を使う**ため、展開後の見た目は現在すでに本番稼働中の「15枚フル表示」と**ピクセル単位で同一**になる（新しい視覚パターンを作らない）。

### 4. 目的チップ→該当カードへのアンカー移動はUX上自然か → **主要ブラウザで自然、フォールバックも設計可能**

HTML標準では、フラグメントナビゲーション（`#id`遷移）の対象が閉じた`<details>`の中にある場合、**ブラウザが自動的にその`<details>`を開いてスクロールする**仕様が定義されており、Chromium系（Chrome/Edge）で実装済み。Firefox/Safariは対応状況にばらつきがあるため、**10行程度の任意の補助JSで100%の一貫性を担保**できる設計にする（4章で詳述）。

### 5. モバイルで初期表示が十分な情報量になるか → **十分**

初期4枚（nosh・ワタミ・三ツ星ファーム・ウェルネスダイニング）は、価格帯（370〜751円）・target（一人暮らし〜糖質制限〜カロリー制限）にばらつきがあり、「同じような商品が4つ並ぶだけ」にはならない。Hero・目的で探す・検証カバレッジで文脈は既に与えられており、4枚は「最初の具体例」として機能する分量。

### 6. 診断ツールとの役割分担が明確になるか → **明確になる**

現状は「TOPで15枚全部見せる」のと「診断で3社に絞る」が同じ情報を重複して提供していた。段階開示後は、**TOP初期表示＝順序どおりの一般的な紹介（6/4枚）、診断＝入力に基づく個別化された3社**という異なる価値提供に分化し、「どちらを使えばいいか」の迷いが減る。

### 7. CTA・広告感・押し売り感が増えないか → **増えない**

「残りを見る」はアフィリエイトリンクではなく、新規のCTAでもない。既存の`.text-link`（`color:var(--color-primary);font-weight:700`、装飾ボタンではない）を流用し、`.btn-primary`（詳しく見る）や外部リンクとは明確に見た目を分ける。新規のアフィリエイトリンク・新規の実CTAは一切追加しない。

### 8. SEO・アクセシビリティ上の問題がないか → **問題ない（むしろ悪化しない設計を選べる）**

- **SEO**：Googleは公式に「アコーディオン内のコンテンツ（JSで動的に読み込むのではなく、最初からHTML内に存在し、CSSで折りたたまれているもの）は通常のコンテンツとして評価する」と明言している。ベストプラクティスは「最初のパネルはデフォルトで開いておく」であり、本設計は**1〜6枚目を`<details>`の外（常時オープン）に置く**ため、このベストプラクティスに合致する。7〜15枚目も静的HTMLとして存在するため、クロール・インデックス自体は妨げない。
- **アクセシビリティ**：ネイティブ`<summary>`要素は`aria-expanded`相当の状態をブラウザが自動管理し、キーボード操作（Tab到達→Enter/Spaceで開閉）・スクリーンリーダーでの状態読み上げが標準で提供される。カスタムJSトグルより実装漏れのリスクが低い。
- 既存のFAQアコーディオン（`service_faq_block()`、`<details class="faq-item">`）が**すでに同じ手法で本番稼働中**であり、実績のあるパターンを再利用するだけ。

### 9. JavaScript依存が過剰にならないか → **過剰にならない（コア機能はJS不要）**

「残りを見る」の開閉そのものは**ネイティブ`<details>`のみで完結し、JSは1行も不要**（既存FAQと同じ）。目的チップ→カードのアンカー精度を100%にするための補助JS（4章）のみ任意で追加するが、これは無くても「該当セクションの近くまでは自動で開いて到達できる」ため、**JSなしでも機能が壊れることはない**（プログレッシブ・エンハンスメント）。

### 10. 既存の15サービスの順序・データ・評価ロジックを完全維持できるか → **完全に維持できる**

実装は「`services`配列を先頭から何番目までを常時表示にするか」という**表示位置の切り分けのみ**で、並び替え・フィルタ・スコアリングを一切行わない。`services.json`の記載順（既存ルール）をそのまま使う。

## 3. 実装設計（案A・確定）

### HTML構造

```html
<div class="service-list-section">
  <h2>📊 主要サービス一覧</h2>

  <!-- 常時表示：1〜4枚目（モバイルもPCもここまでは常に見える） -->
  <div class="service-grid">
    <div class="svc-card svc-card-top" id="svc-nosh">...</div>
    <div class="svc-card svc-card-top" id="svc-watami-takushoku">...</div>
    <div class="svc-card svc-card-top" id="svc-mitsuboshi-farm">...</div>
    <div class="svc-card svc-card-top" id="svc-wellness-dining">...</div>
    <!-- 5・6枚目：PCのみ常時表示、モバイルは非表示（後述CSS） -->
    <div class="svc-card svc-card-top svc-extra-initial" id="svc-shokutakubin">...</div>
    <div class="svc-card svc-card-top svc-extra-initial" id="svc-fit-food-home">...</div>
  </div>

  <!-- 7〜15枚目：ネイティブdetailsで折りたたみ（JS不要、既存FAQと同じ仕組み） -->
  <details class="svc-more">
    <summary>残り9社をすべて見る</summary>
    <div class="service-grid">
      <div class="svc-card svc-card-top" id="svc-magokoro-care">...</div>
      <!-- ...以下、7〜15枚目。既存ループの出力をそのまま流用 -->
    </div>
  </details>
</div>
```

- `id="svc-{service['id']}"`をカード生成ループに1属性追加するのみ（`build_index_page()`内、既存の`f'<div class="svc-card svc-card-top">'`を`f'<div class="svc-card svc-card-top" id="svc-{svc[\"id\"]}">'`に変更）。id衝突は既存コード内に無いことを確認済み。
- 5・6枚目のみ`svc-extra-initial`クラスを追加で付与（インデックス4・5番目の時だけ）。
- 7枚目以降は現状と同じループ出力を、`<details class="svc-more">`の中の**2つ目の`.service-grid`**にそのまま入れる（コピーではなく、同じforループの後半部分の出力先を分けるだけ）。

### CSS

```css
/* 5・6枚目：PC(900px以上)でのみ常時表示。モバイルは.svc-moreの中と同じ扱いにしないよう、
   .svc-extra-initialは.svc-moreの外側に置いたまま、CSSで表示/非表示のみ切り替える */
.svc-extra-initial { display:none; }
@media (min-width:900px) {
  .svc-extra-initial { display:flex; } /* .svc-cardのdisplay:flexに合わせる */
}

/* 残りを見る：.faq-itemの既存パターンを流用し、ボタンではなくテキストリンク調にする
   （実CTAの.btn-primaryと混同させないため）。押し売り感を出さない中立トーン。 */
.svc-more { margin:var(--space-4) 0; border:none; }
.svc-more summary {
  cursor:pointer; list-style:none; text-align:center;
  padding:var(--space-3); font-weight:700; color:var(--color-primary);
  border:1px solid var(--color-border-strong); border-radius:var(--radius-sm);
}
.svc-more summary::-webkit-details-marker { display:none; }
.svc-more summary::after { content:" ▾"; }
.svc-more[open] summary::after { content:" ▴"; }
.svc-more[open] summary { margin-bottom:var(--space-3); }
.svc-more .service-grid { margin:0; }
```

- 新しい色トークンは使わない（`--color-primary`/`--color-border-strong`など既存トークンのみ）。
- 開閉のアニメーションは付けない（既存の`.faq-item`も高さアニメーションなし。`<details>`の高さアニメーションはブラウザ間で不安定なため、既存の流儀に合わせて瞬時に開閉させる。`prefers-reduced-motion`を考慮する必要がある新規アニメーションを増やさない）。

### JavaScriptが必要か

**コア機能（開閉）は不要。** 既存のFAQアコーディオンと同じくブラウザのネイティブ機能のみで完結する。

**任意の補助JS（約10行、無くても機能は壊れない）**：目的チップから7枚目以降のカードへアンカー遷移した際、Firefox/Safariなど自動オープンに対応しないブラウザでも確実に開くようにする場合のみ追加する。

```html
<script>
(function(){
  var id = location.hash.slice(1);
  if (!id) return;
  var el = document.getElementById(id);
  var details = el && el.closest('details.svc-more');
  if (details && !details.open) details.open = true;
})();
</script>
```

- 既存の診断ツール（`build_diagnosis_tool()`）も同様のインラインJSパターンを既に使っており、技術的に新規要素ではない。
- **このJSが無い場合**：Chromium系ブラウザ（Chrome/Edge、国内シェア過半数）ではネイティブ挙動で問題なく動作。非対応ブラウザでは「`<summary>`（残りを見るボタン）の位置まではスクロールされるが、自動では開かない」という**軽微な劣化**に留まり、ユーザーがもう1クリックすれば見える＝機能が失われるわけではない。

### アンカー方式

- 目的チップ配下の各サービスリンク（`purpose_chips_block()`が生成する`<a href="/services/{id}.html">`）は**変更しない**（既存の詳細ページへの直リンクを維持）。
- 新たに、各リンクのすぐ隣に「↓一覧で見る」という**同ページ内アンカー**を追加する（`<a href="#svc-{id}" class="text-link" style="font-size:12px;">`程度の軽微な追加）。既存リンクを置き換えるのではなく**選択肢を1つ追加する**形にし、詳細ページに直接行きたいユーザーの動線は変えない。

### 展開時の挙動

- クリック（またはEnter/Space）で`<details>`が開き、7〜15枚目が**現在と全く同じ`.service-grid`のCSSで**即座に表示される。
- 開いた状態はページ内では保持されるが、ページ再読み込みでは初期状態（閉）に戻る（`sessionStorage`等での状態保持は新規機能追加になるため今回のスコープ外とする）。

### モバイル挙動

- 初期表示は1〜4枚目のみ（5・6枚目は`svc-extra-initial`によりモバイル幅では`display:none`）。
- 「残りを見る」をタップすると、5〜15枚目（11枚）が一括で展開される。モバイルでは5・6枚目と7〜15枚目を分けて段階開示する設計にはしない（実装・QAが複雑になるだけで、5章で述べたとおりモバイルの初期表示は4枚で十分と判断済みのため）。
- タップ領域は`.svc-more summary`のpadding（`var(--space-3)`＝12px）＋テキスト行で44px以上を確保する。

### キーボード／アクセシビリティ

- `<details>/<summary>`は追加のARIA属性なしで、Tabキーでのフォーカス・Enter/Spaceでの開閉・スクリーンリーダーでの状態通知（「折りたたみ済み／展開済み」相当）がブラウザ標準で提供される。
- アンカーリンク（「↓一覧で見る」）もフォーカス可能な通常の`<a>`要素であり、追加のキーボードトラップ等は発生しない。
- 新規に`tabindex`や独自の`role`を設定する必要はない。

### noscript時の扱い

- JS無効環境でも「残りを見る」の開閉は**そのまま動作する**（ネイティブ機能のため）。
- 任意の補助JS（アンカー精度向上）が動かない場合も、4章で述べたとおり機能停止ではなく軽微な精度低下のみ。
- `<noscript>`タグによる代替コンテンツの用意は不要（そもそもJSに依存する機能がコアには無いため）。

### 既存ページへの影響

- 変更は`build_index_page()`（TOPページ生成関数）のみに閉じる。`.svc-more` `.svc-extra-initial`はいずれもTOP専用の新規クラスで、他ページ（ranking.html・詳細ページ・診断・比較ページ）のHTML生成コードには一切登場しない。
- 第1段階の実装で確立した「TOP専用クラスは他ページのHTML本文に出現しないことをビルド後にgrepで確認する」という検証手順（`docs/TOP_LAYOUT_IMPLEMENTATION_PLAN_2026_08_28.md`実施時と同様）を、実装時にも踏襲することを推奨する。
- `_meal_form_note`・`aff_link()`・`_price_inline_html()`・検証ロジック・`services.json`の読み込み処理はいずれも無変更。

## 4. 最終判定

# **このまま実装してよい**

「PC6／モバイル4／残りを見る」という前回確定案の**方針・件数は維持**する。ただし本監査で以下の点を具体化・強化した：

1. 実装手段を、前回の「軽量JS」という曖昧な想定から、**「ネイティブ`<details>/<summary>`のみでコア機能を実現し、JSは任意の補助（無くても壊れない）」**という、より制約に強く適合する具体設計に格上げした。これは方針変更ではなく、既にサイト内で実績のある手法（`service_faq_block()`のFAQアコーディオン）への統一である。
2. PC6・モバイル4という数値を、A/B/C/Dの4案比較によって「感覚」ではなく「視認性・スクロール量・選択負荷・診断との役割分担・実装リスク」の5軸で裏付けた。
3. 目的チップ→カードのアンカー連携が、HTML標準のネイティブ挙動でブラウザの過半数（Chromium系）において追加実装なしに機能することを確認し、残りのブラウザ向けの任意フォールバックも設計した。

以上により、**設計の手戻りは不要**と判断する。次のステップ（実装）に進む場合は、本書3章のHTML/CSS/JS設計をそのまま使用できる。

## 5. 制約適合の最終チェックリスト

| 制約 | 適合 |
|---|---|
| data/*.json・config/*.json変更禁止 | ✓ 無変更（表示位置の切り分けのみ） |
| サービス順序・既存データ・スコアリング変更禁止 | ✓ services.json記載順をそのまま使用、新規ソートなし |
| affiliate href/rel/計測ロジック変更禁止 | ✓ `aff_link()`は無変更、呼び出し箇所も変更なし |
| SEO title/canonical等変更禁止 | ✓ 無変更。むしろアコーディオン内コンテンツのSEOベストプラクティス（最初のパネルは開いておく）に合致 |
| ★評価・独自ランキング等の新設禁止（更新後の制約） | ✓ 新規評価基準を導入していない。既存順序のみを使用 |
| 新規サービス情報の追加禁止 | ✓ 新規データ項目なし |
| 他ページへの不要な波及禁止 | ✓ 新規クラスはTOP専用、他ページのコード生成には非登場 |
| 既存の診断ロジック変更禁止 | ✓ `build_diagnosis_tool()`は無変更（役割分担が明確になるだけ） |
| 大規模な機能追加禁止 | ✓ 開閉UIは既存パターンの再利用、補助JSも10行程度に限定 |

## 1. 現状TOPの問題点（優先順位付き）

### 1位：15枚のカードが「発見」段階のまま全部同格で並び、選択過多（choice overload）を誘発している

実測：service-list-sectionの高さはPCで1192px（実質、画面5行分をスクロールしないと全15枚に到達しない）、**モバイルでは3702px＝ビューポート4.6画面分**。PCファーストビュー（900px）には1枚もカードが完全表示されず、部分的に3枚見えるのみ。

一方、本サイトには既に**診断ツール（`/tool/diagnosis.html`）という「選択肢を絞る」ための正解の仕組みが実装済み**で、実際に「あなたの条件に近い上位3社」という理想的な出力をしている（第1段階監査でも実機確認済み）。にもかかわらずTOPの主要導線は、この診断とは無関係に**15社をフルスペックのカードで全部並べる**という、診断ツールの存在意義と競合する設計になっている。

Web調査（後述）の一致した知見：「レコメンドは3〜4件に絞る」「Amazonも画面サイズに応じて4〜7件に絞る」「一覧は選択肢過多を招く」。現状のTOPはこの原則と逆方向（全件を一度に露出）になっている。

### 2位：「目的で探す」チップと「サービス一覧」が完全に独立した別導線になっている

実測：チップ配下のリンク（例：`シェフの無添つくりおき`→`/services/chef-muten-tukuritoki.html`）はすべて**詳細ページへの直リンク**で、下の「主要サービス一覧」グリッドとは一切接続していない。ユーザーが「一人暮らし」チップを見て興味を持った情報が、その下のカード一覧に何も反映されない（同じ15枚がもう一度、無関係に並ぶだけ）。目的による絞り込みという行為が、一覧を見る行為の助けになっていない。

### 3位：「15サービスの見せ方」が意思決定ファネル上のTOPの役割（発見）と、比較一覧ページの役割（評価）を重複させている

`UI_DESIGN_PRINCIPLES.md` 3.1節は明確に「TOP＝発見・要件形成」「比較一覧＝スクリーニング＋評価」と役割分担を定義している。しかし現状のTOPカードは、詳細ページ・比較一覧ページとほぼ同じ情報量（価格・検証バッジ・タグ・向いている人・2CTA）を15枚フルで持っており、実質的に「簡易版の比較一覧ページ」をTOP内にもう1つ作ってしまっている。原則が定義する役割分担と実装が一致していない。

### 4位（構造的ではないが明確）：カード単体の視覚設計は既に妥当だが、それゆえ「15枚を読み比べる」以外の使い方を用意していない

第1段階の再設計で各カードの内部階層（名前+価格→target→タグ→CTA）は改善済み。しかし個々のカードの質が上がったことで、逆に「全部丁寧に作られているので、全部読まなければいけない気になる」という副作用が生まれている。情報設計としては、**個々のカードの改善はもう十分**で、次の課題は「何枚見せるか」「どの順で見せるか」という一段上のレイヤーにある。

### 5位（軽微）：診断への誘導が「Heroのボタンの1つ」に留まり、来訪目的に応じた強調がされていない

Hero内の2CTA（診断=primary、比較一覧=secondary）自体の階層は妥当（後述、変更不要と判断）。ただし診断ツールが持つ「3〜4件に絞る」という強みが、Hero文言・ボタン文言だけでは伝わらず、その下に15枚の一覧が待ち構えているため、「どうせ全部見せられるなら診断は要らないのでは」という印象を与えかねない。

## 2. 競合・海外/国内の優れたUIパターン（Web調査）

| パターン | 内容 | 出典 |
|---|---|---|
| **レコメンド件数の上限** | 高コンバージョンのクイズ/診断ファネルは「3〜4件」に推奨を絞る。Amazonも画面サイズに応じ4〜7件に制限し選択過多を回避 | ConvertFlow, cultmethod |
| **Progressive Disclosure（段階開示）** | 初期表示は主要な項目のみ、残りは「もっと見る」で展開。「最初に表示されるという事実自体が、それが重要だというシグナルになる」 | NN/G, LogRocket |
| **単一の主要CTA＋メッセージの一貫性＋速度** | 2026年のCROで最もレバレッジが高い施策は「message-match」「表示速度」「フォーム短縮」「ファーストビューの社会的証明」「単一の主CTA」の5つ | Leadfeeder, Apexure |
| **Editor's Pick的な強調は"控えめに"** | 比較表で推奨を目立たせる場合も、支配的な視覚重み付けではなく「バッジ1つ・背景色を淡く」程度に留めるのが2026年の標準。過度な強調はバイアスに見える | LogRocket UX, Webstacks |
| **モバイルはデスクトップよりコンバージョンが40〜51%低い** | モバイルでの情報量・スクロール量の設計は特に重要 | Leadfeeder |

## 3. 現在のTOPに適用可能なパターン

| パターン | 適用可否 | 理由 |
|---|---|---|
| 表示件数の段階開示（Progressive Disclosure） | **適用可** | 既存順序・既存データのまま「初期表示数」だけを変える。新規スコアリング不要 |
| 目的チップ→一覧内アンカー連携 | **適用可** | 既存の`purpose_matches`・`services`データのみで実現可、新規データ不要。クリックでスクロール＋一時ハイライトは軽量CSS/JSで足りる |
| 単一主CTA・メッセージ一貫性 | **既に適用済み**（変更不要） | Heroの2CTA構成は既にprimary1つ+secondaryリンク1つで、原則と一致 |
| モバイル軽量化優先 | **既に一部適用済み**（段階開示でさらに強化余地あり） | 第1段階でモバイル圧縮済み。件数を絞ることで更なる恩恵 |
| Editor's Pickの視覚的強調 | **不採用** | サイトの恒久方針（★評価・ランキング禁止）と衝突するため |
| 診断結果への事前パラメータ渡し（チップ→診断ツールへ選択済み状態で遷移） | **条件付き不採用** | 診断ツールが現状クエリパラメータでの事前選択に対応しておらず、対応させるには新規ロジックの実装が必要＝「大規模な機能追加はしない」制約に抵触するリスクが高い |

## 4. 「残す／削る／移動／統合／強調」の判断

| 対象 | 判断 | 理由 |
|---|---|---|
| Hero（見出し・リード・2CTA） | **残す（変更しない）** | 単一主CTA＋メッセージの一貫性という2026年CROの最重要施策に既に合致。第1段階で余白も最適化済み |
| 目的で探す（ゾーン自体・チップ・カテゴリ） | **残す＋強調**（一覧との連携を強化） | データ・カテゴリ・遷移先は無変更のまま、「一覧内アンカーへのスクロール」機能を追加してチップの効力を上げる |
| 検証カバレッジ（compact帯） | **残す（変更しない）** | 第1段階で既に「主役にしないが信頼材料として残す」設計が完了している。社会的証明としてファーストビュー付近に既にある |
| サービス一覧（15枚フルカード） | **削る（初期表示件数を絞る）** | 全件を一度に見せることが最大の問題。個々のカードの情報量・優先順位（名前+価格→target→タグ→CTA）自体は変更しない |
| 「全15社を比較する」導線 | **強調** | 段階開示の「もっと見る」到達点、またはHeroのsecondary CTAとして、比較一覧ページへの遷移をこれまで以上に明確な出口にする |
| キャンペーン・このサイトのこだわり（その他既存要素） | **残す（変更しない）** | 第1段階でサービス一覧の後段に移動済み。役割・位置とも妥当 |
| 個別カードの内部レイアウト（D節、名前+価格→target→タグ→CTA） | **残す（変更しない）** | 第1段階の設計のまま。カード単体の質は既に十分 |
| 目的チップ配下のカテゴリ別ミニプレビュー（新設） | **統合を検討したが不採用** | `compute_purpose_matches()`はカテゴリ間で重複あり・max_items=4固定であり、これを流用して一覧を再構成すると同じ社が複数回出現し、かえって情報量が増える。5章で「案2」として比較のうえ不採用と結論 |

## 5. 改善案 3案比較

### 案1：表示件数の段階開示（Progressive Disclosure）＋ チップ→一覧アンカー連携

- サービス一覧の初期表示を**6枚**（services.json記載順のまま、先頭6件。ソート変更なし）に絞り、「残り9社をすべて見る→」ボタンで同じグリッド内に残りを展開する（軽量JS、非表示要素の`display`切り替えのみ）。
- 目的チップの各リンクの隣（またはチップ自体）に、対応するサービスが一覧内の何番目かを示す**アンカーリンク**を追加し、クリックで一覧内の該当カードまでスクロール＋一時ハイライト（CSS `outline`点滅程度、新規データ不要）。既存の詳細ページへの直リンクは維持し、アンカー機能は追加の選択肢として提供する。
- Hero・検証カバレッジ・キャンペーン・こだわりは無変更。

### 案2：目的別プレビュー＋全件は比較一覧へ委譲（役割分担の徹底）

- 「主要サービス一覧」セクションをTOPから撤去し、代わりに目的チップの各カテゴリ直下に、該当社の最小プレビュー（名前+価格+検証バッジのみ）を1〜2枚ずつ埋め込む。
- 「全15社を比較する→」を比較一覧ページへの主要な出口として大きく配置。
- Hero・検証カバレッジは無変更。

### 案3：診断を絶対的な主役にするHero再構成

- Hero直下に、目的チップの主要カテゴリ（5〜7個）を診断ツールへの事前選択リンクとして統合。
- サービス一覧は案1同様に段階開示で圧縮。

| 評価軸 | 案1（段階開示＋アンカー連携） | 案2（目的別プレビュー統合） | 案3（診断主役化） |

| 選択過多の解消 | ◎ 初期6枚まで削減 | ○ カテゴリ単位では絞られるが総露出数はカテゴリ数×重複で増える可能性 | ◎ 診断に誘導できれば最も強力 |
| 目的で探すの実効性強化 | ○ アンカー連携で一定の強化 | ◎ チップ自体が結果を内包し最も強力 | ○ 診断への橋渡しとして強化 |

## 6. 最も推奨する案

**案1（表示件数の段階開示＋チップ→一覧アンカー連携）を推奨する。**

理由：
1. **制約適合度が最も高い**：新規データ・新規スコアリング・大規模機能のいずれにも該当せず、「今回の監査は提案のみ」という制約下でも最も具体的に実装イメージが描ける。
2. **選択過多の解消という最重要課題に直接効く**：初期6枚（実測ベースで概算するとPCファーストビューにちょうど収まる枚数に近い）に絞ることで、Web調査で確認した「3〜4〜7件」という推奨レンジに現実的に近づけられる。
3. **透明性の原則と両立する**：`UI_DESIGN_PRINCIPLES.md`が重視する「少ない数字も隠さない」「15社掲載」という誠実さを、件数を削るのではなく「初期表示を絞り、明示的な操作で全件に到達できる」形で守れる。
4. **案2・案3の良い部分を将来的に段階的に取り込める土台になる**：まず案1で「絞る」型UIの実効性をPlaywright/実運用で検証し、効果が確認できれば案2（チップ内プレビュー）や案3（診断連携）を追加検討する、という安全な進め方ができる。

## 7. PC／モバイルの具体的レイアウト案（案1）

### PC（1440px基準）

```
📊 主要サービス一覧
┌────────┐┌────────┐┌────────┐
│ Card 1 ││ Card 2 ││ Card 3 │  ← services.json先頭6件（順序不変）
```

- 目的チップの各サービスリンクの隣に、小さな「↓一覧で見る」アンカー（初期表示6枚に含まれる場合は一覧まで、含まれない場合は展開後にスクロール＋展開を自動実行）を追加。

### モバイル（375px基準）

```
📊 主要サービス一覧
Card 1
Card 2
Card 3
Card 4          ← 初期表示4枚（1列のため縦の占有を考慮しPCより少なめ）
[ 残り11社をすべて見る ▾ ]
Card 5〜15（展開後）
```

- モバイルは1カードあたりの高さがPCより大きいため、初期表示は6枚ではなく**4枚**を目安とする（実測ベースの概算。実装時にPlaywrightで最終調整）。
- 「残り◯社を見る」ボタンはタップ領域44px以上を確保（既存`.btn-secondary`の`min-height:44px`をそのまま流用）。

## 8. 既存データ・機能を維持したまま実現できる実装範囲

- 対象は`tools/sitegen/templates.py`の`build_index_page()`のみ。データ取得・`services`の順序・`aff_link()`・`_price_inline_html()`等は無変更。
- 追加が必要なもの：
  - サービスカードループに「最初のN件は表示、以降は`hidden`クラス付与」という条件分岐（Nは定数、PC/モバイルは同一DOMに対しCSSの`@media`で挙動を分けるか、JS側でviewport幅を見て初期件数を出し分ける）
  - 「残り◯社をすべて見る」ボタン1つ（クリックで`hidden`クラスを外すだけの数行のJS。診断ツールで既に使っているものと同種の軽量な操作であり、新規の技術要素ではない）
  - 目的チップ→一覧アンカーの`id`属性をカードに付与（`id="svc-{service.id}"`程度）し、チップ側に`href="#svc-{id}"`を追加するだけ。新規JSはスクロール後の一時ハイライト（CSSアニメーション、`prefers-reduced-motion`配慮）のみ。
- **変更不要**なもの：`data/services.json`・`config/*.json`・`aff_link()`・CTA遷移先・SEO/canonical・検証ロジック・カード内部レイアウト（D節）・Hero・検証カバレッジ・キャンペーン・こだわりセクション。

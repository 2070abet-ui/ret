## 0. 先に結論

**移行する。** Phase1〜4を通じて、MUST MATCHのギャップは解消され、DIFFERENTIATEは1系統（値単位の確認可能性＋全社横断ダッシュボード）に確立・実装済みである。Phase4の競合再監査では新規のDIFFERENTIATE候補が**ゼロ件**という結果が出た（6条件テストで全候補が脱落）。これは調査不足ではなく、「作るべきものを作り切った」ことの裏付けと判断する。

これ以上機能を探し続けることは、機能追加そのものが目的化するリスクを生む。Phase4以降は **計測 → データ品質 → CV導線改善 → 実測 → 改善** のループへ移行する。

## 1. GA4最小イベント設計

### 1.1 まず確認したこと：GA4の「拡張計測機能」で何が無料で取れるか

GA4は計測タグを設置するだけで、**拡張計測機能（Enhanced Measurement、デフォルトで有効）**により以下をコード0行で自動計測する。

| 自動計測イベント | 内容 |
|---|---|
| `page_view` | 全ページビュー。ページパスの遷移列から「どのページを経由したか」がGA4標準のパス探索レポートで追える |
| `scroll` | 90%スクロール到達 |
| `outbound_click`（GA4内部名は`click`＋`outbound:true`パラメータ） | **現在のドメイン以外へのリンククリックを自動検知**。`link_url`（遷移先URL）・`link_domain`・`link_text`パラメータ付き |

`aff_link()`が生成するリンク（A8トラッキングURLまたは各社公式ドメイン）は**すべて他ドメインへのリンク**であるため、この`outbound_click`がユーザー指定の`outbound_cta_click`の要件（「どのページ・導線が公式サイトクリックにつながっているか」）を**追加コード無しで満たす**。`link_url`にA8の`a8mat=`パラメータや各社公式ドメインがそのまま入るため、どのサービスへのクリックかはURLパターンで判別可能（サービスIDとURLの対応表を別途ドキュメント化すれば十分。コード側にdata属性を追加する必要は無い）。

同様に、`internal_nav_click`（サイト内のどの導線を辿ったか）も、GA4標準の`page_view`の遷移列（パス探索・セッション経路レポート）で代替可能。**独自のクリックイベントとして実装する必要性は無い**。

### 1.2 結論：ユーザー提案の4イベントのうち、独自実装が必要なのは2つだけ

| 提案イベント | 判定 | 理由 |
|---|---|---|
| `outbound_cta_click` | **実装不要（拡張計測の`outbound_click`で代替）** | 独自コードを書くとGA4標準機能と二重計測になり、「イベントを増やすこと自体が目的」になる典型例。採用しない |
| `internal_nav_click` | **実装不要（`page_view`のパス探索で代替）** | 同上 |
| `diagnosis_start` | **独自実装が必要** | 診断ツールはページ遷移を伴わないクライアントサイドの操作（チェックボックス選択→ボタン押下→結果表示）であり、GA4の拡張計測機能はこれを検知できない |
| `diagnosis_complete` | **独自実装が必要** | 同上 |

**追加提案イベントは無し。** 4つに絞ることが目的ではなく、「本当に自動計測で取れないものだけ」を残した結果が2つになった。

### 1.3 独自イベントの最小設計（実装は次フェーズ、今回はコード変更しない）

現行の`tool/diagnosis.html`（`build_diagnosis_tool`、`templates.py`）のJSにフックする。

```js
// 診断ツール開始（初回のチェック操作のみ。多重発火防止のフラグを1つ持つだけ）
let _diagStarted = false;
document.querySelectorAll('#goals input, #mealforms input').forEach(el => {
  el.addEventListener('change', () => {
    if (!_diagStarted) {
      _diagStarted = true;
      gtag('event', 'diagnosis_start');
    }
  });
});

// 診断完了（runDiag()の末尾、結果描画の直後に1行追加するだけ）
gtag('event', 'diagnosis_complete', {
  goal_count: goals.length,
  mealform_count: mealForms.length,
  result_count: scored.length
});
```

- 新規のデータモデル・新規ページは無い。既存の`runDiag()`関数末尾への1行追加と、チェックボックスへのイベントリスナー1箇所のみ。
- `result_count`により「診断したが0件だった」ケースも区別できる（診断ツールの実用性を測る上で重要）。
- サービスIDまで送る必要は無い（診断結果は複数件あり得るため、個社への遷移は上記1.1の`outbound_click`側で捕捉される）。

### 1.4 実装条件（今回は行わない）

GA4プロパティ作成・測定IDの取得はユーザー側の作業。`config/site.json`に測定IDを追加し、`page_header`にgtag.jsスニペットを1箇所追加する程度で導入可能（Phase3までの`site.json`拡張パターンと同型）。

「独自だから残す」ではなく、収益・信頼形成への寄与可能性で評価する。

| 項目 | 競合との差 | ユーザー価値 | CVへの寄与仮説 | 運用コスト | 今後 |

| 値単位の出典＋確認日リンク | 5競合サイト実地確認で5サイトとも未実装（Phase3・Phase4の2回にわたり再検証済み） | 中〜高。ただし**大半のユーザーは意識的にクリックしない可能性が高い**（出典リンクのクリック率は未計測）。効果は「クリックされること」より「その場に存在することで生まれる漠然とした信頼感」という間接効果の比重が大きいと推測される（計測不能な効果） | 中（仮説）。YMYL隣接ジャンルのE-E-A-T効果として一般に語られるが、当サイト固有の効果は未検証 | **極めて低い**（10マス、既存データの参照のみ。新規収集不要） | **維持**。コストがほぼゼロで下げる理由が無い。ただしクリック率計測（GA4導入後）をKPIとして追加し、実際に使われているか初めて検証する |

| 全社横断verification dashboard（`/verification.html`） | 5競合サイト実地確認で5サイトとも未実装（Phase4新規検証） | 中。一覧性はあるが、**このページ単体に到達する動線が弱い**（脚注リンクのみ）ため、現状の実利用者数は恐らく非常に少ない | 低〜中（仮説）。直接CVページではなく、信頼性の「証拠」を求める一部のユーザー・場合によってはASP審査担当者向けの効果に留まる可能性がある | 低（既存ロジックの再利用のみで新規実装済み） | **維持するが、過大評価しない**。GA4導入後、`/verification.html`のページビュー数とそこから各サービス詳細への遷移率を計測し、実際に見られているか確認する。見られていなければ「作ったが使われていない」という結論も受け入れる |

**総括**: 3項目とも運用コストが極めて低いため「残すコスト」自体はほぼゼロ。判断の核心は「効果があるかどうか分からない」という点にあり、これはコードの良し悪しではなく**計測基盤が無いことそのものが原因**。したがって1章のGA4導入が、この評価を「仮説」から「実測」に格上げする唯一の方法である。

## 3. Phase4の3候補：最終採点

| 項目 | ROI | 実装コスト | データ依存性 | CV寄与 | 差別化寄与 | 判定 |
|---|---|---|---|---|---|---|
| A. GA4計測基盤 | 高（2章の3項目すべての評価を実測に変える前提条件） | 低（タグ設置＋2イベントのみ） | 無し（ユーザーがGA4プロパティを用意） | 間接（測定基盤自体はCVを生まないが、以後の全ての改善判断の前提） | 無し（差別化施策ではなくインフラ） | **GO** |
| B. 出典リンク接続漏れ修正（nosh・食宅便の送料） | 低〜中（対象2社×1フィールドのみ） | 極めて低（`data/shipping.json`に`source_id`を2行追加するのみ、テンプレート変更不要） | 無し（`sources.json`に該当エントリ`nosh-shipping-202608`・`shokutakubin-shop-202608`が既存） | 無し（両社とも非提携、CV導線に乗らない） | 低（既存差別化の完成度を上げるのみ） | **GO（条件付き、3.1節）** |
| C. モバイル横スクロール案内文言 | 低（コストがほぼ0なので期待値はプラスだが効果は未測定） | 極めて低（テキスト1行） | 無し | 低（離脱防止の可能性） | 無し | **GO** |

### 3.1 Bの判断：Rule of Threeからの逸脱にあたるか

**GO、ただしRule of Threeの解釈を明確化した上で実施する。**

Rule of Three（A8承認5社の3フィールドに限定）が禁止していたのは、**未確認の情報を新たに収集する労力を非収益サービスにまで広げること**である。今回のnosh・食宅便の送料は、この禁止事項に該当しない。

- 両社の送料は既に確認済み（`shipping_line()`で本文表示済み）であり、**新規の一次情報収集は発生しない**。
- 対応する出典（`nosh-shipping-202608`／`shokutakubin-shop-202608`）は`sources.json`に既存。
- 実装は`data/shipping.json`へのキー追加のみで、コード変更もゼロ。

つまりこれは「Rule of Threeの対象拡大」ではなく、「既に表示している情報に、既に持っている出典を紐付けるだけの記帳漏れの是正」である。**Rule of Threeの文言（4フィールド→対象社拡大の禁止）は、新規の一次情報収集を伴う場合にのみ適用されると解釈を明確化する**。今後、同様に「値は確認済みだが出典リンクが未接続」なセルが見つかった場合も、同じ基準（新規収集ゼロ・非収益社2社程度の小規模）で個別に判断してよい。ただし、これを恒常的な拡大ルートとして扱わない（「小規模なら際限なく増やしてよい」という運用に転化させない）ことを明記する。

## 4. データ品質の優先順位

「このデータ欠損を埋めるとユーザーの意思決定またはCVが改善するか」を基準に、A8提携状況（＝実際にCVが発生しうるか）を最重要変数として並べ替えた。

| 優先度 | サービス | 欠損データ | A8提携 | 優先理由 |
|---|---|---|---|---|
| 1 | yoshikei | price | **提携済み** | 提携済みなのに価格が11社中最後まで空欄。埋まればCVページとしての説得力が上がる。**price confirmed/derivedが現在4/11→これを含め2社埋まれば6/11に到達し、DEFER中のranking.html価格ソートの着手条件を満たす** |
| 2 | fit-food-home | official domain | **提携済み** | 価格・送料・記事内リンクなど**複数フィールドがこのドメイン確定待ちでブロックされている前提条件**。ここを解かない限り他の欠損も埋まらない |
| 3 | fit-food-home | price / shipping | **提携済み** | 優先度2の後続。優先度1と合わせて確定すればranking価格ソートの条件（6/11）を満たす組み合わせの一つ |
| 4 | nosh | price（再確認） | 未提携（ただし比較ページ2本の主役） | CVには直結しないが、ブランド認知度が11社中最高で、比較ページ・将来のSEO記事の情報的完成度に効く。「492円」という公式サイトの宣伝文言と実際のプラン価格が食い違うという固有の問題（Phase1で既に一次記録あり）の解消が必要 |

| 8 | 高齢者Theme関連5セル（食楽膳やわらか食対応／健康直球便個食対応／まごころケア食3軸） | tags/main_features未確認 | 一部提携 | Theme本体はPhase4監査でDEFER継続（競合規模拡大によりさらに劣位）と判定済みのため、**データが埋まってもTheme公開に直結しない**。優先度は最下位 |

## 6. 次フェーズの目的の再定義

### 6.1 Phase1〜3の目的（達成済み）
競合水準へのキャッチアップ（MUST MATCH解消）＋独自基盤構築（値単位出典・検証状況ダッシュボード）。

### 6.2 Phase4以降の目的
**計測 → データ品質 → CV導線改善 → 実測 → 改善** のループへ移行する。

### 6.3 自己監査：機能追加が目的化していないか

Phase1〜3は毎フェーズ何らかの新規実装を伴っており、「前フェーズで何かを作ったから今フェーズも何か作る」という慣性が生まれるリスクがあった。Phase4の競合再監査（6条件テスト）で新規DIFFERENTIATE候補がゼロ件という結果が出たことは、**この慣性を断ち切る正しいシグナル**として扱う。今回、3候補（GA4・出典接続漏れ・モバイル案内文言）はいずれも「新機能」ではなく「計測基盤」「既存機能の完成度」「軽微なUX是正」であり、新規の差別化機能は1件も含まれていない。これは意図した結果である。

## 7. まとめ

### 1. Phase1〜4で確立したもの
- MUST MATCH解消（比較表・確認日表示・関連サービス・CTA階層・モバイル対応の基礎・診断ツール・比較ページ内部リンク）
- DIFFERENTIATE: 値単位の出典＋確認日リンク、全社横断verification dashboard

### 2. 競合との差別化として残すもの
- 値単位の出典＋確認日リンク（2章で維持と判定）
- 全社横断verification dashboard（同上、ただし過大評価しない）

### 3. 競合コピーとして十分なもの（MUST MATCH水準で完了、追加投資不要）
- 関連サービスブロック、CTA階層、比較ページ、診断ツール（対話式・チェックボックス型）、verification-statusバッジ

### 4. 今後作らないもの
5章参照。減塩/無添加/高タンパクTheme・口コミ機能・比較社数拡大競争・推薦エンジン・matching DSL・Theme汎用エンジン・UpdateLog基盤・高度な計測基盤は恒久DO NOT BUILD。高齢者Themeは事実上のDO NOT BUILDに近いDEFER。

### 5. GA4最小イベント設計
拡張計測機能（無料・コード0行）で`outbound_click`・`page_view`ベースの経路分析をカバーし、独自実装は`diagnosis_start`・`diagnosis_complete`の2つのみ（1章）。

### 6. データ品質優先順位
収益化済み2社（yoshikei価格・fit-food-homeドメイン確定＋価格/送料）を最優先。magokoro-careのcampaignは優先度5（CVに直結しないが3フェーズ放置の是正）。watami/mitsuboshi/wellness-diningは非収益かつ技術的障壁があるため最後（4章）。

### 7. Phase4実装GO/NO-GO
A（GA4）: GO。B（出典接続漏れ）: GO（Rule of Three解釈を明確化した上で、3.1節）。C（モバイル案内文言）: GO。3件とも新機能ではなく計測基盤・完成度向上・軽微UX是正であり、新規差別化機能はゼロ。

| `diagnosis_start`→`diagnosis_complete`の完了率 | 診断ツールが実際に最後まで使われているか |
| `diagnosis_complete`の`result_count=0`比率 | 診断条件が厳しすぎて候補が出ない割合（UX課題の検知） |
| `/verification.html`のページビュー数・そこからのservice詳細への遷移率 | 検証状況ダッシュボードが実際に見られ、使われているか（2章で「過大評価しない」とした判断の検証） |
| 出典リンク（`source_link`）のクリック率 | 値単位の出典表示が実際に使われているか |

### 9. 実装順序
1. GA4プロパティ作成（ユーザー側作業）→ 測定ID発行
2. `config/site.json`への測定ID追加＋`page_header`へのgtag.js設置（低リスク）
3. 診断ツールへの`diagnosis_start`/`diagnosis_complete`実装（1.3節の設計をそのまま反映）
4. 出典リンク接続漏れ修正（nosh・食宅便の送料、`data/shipping.json`への`source_id`追加2行）
5. モバイル横スクロール案内文言の追加
6. 2〜3週間のベースライン計測期間を確保
7. ベースラインを見た上で、データ品質優先順位（4章）に沿ってyoshikei価格・fit-food-homeドメインの確認作業を継続
8. GA4データが十分に蓄積した時点で、DEFER中の項目（JSON-LD拡充、CTA文言最適化、ranking価格ソート）の着手可否を実測に基づいて再判断する

新機能の追加はこのリストに含まれていない。これは意図的な判断である。

## 1. Product thesis

**宅食図鑑は「宅配食を最も広く網羅するサイト」ではなく、「11社という手の届く範囲を、フィールド単位で検証しながら継続的に正確に保つサイト」である。**

競合の多くは「情報量」か「実食体験」のどちらかで戦っている（my-best等は量、single-meallife.com/takushoku-repo.comは実食写真）。個人運営でこの2つを同時に取りに行くのは無理がある。宅食図鑑が取るのは第三の軸=**「この数字は本当に確認できているか」を隠さず、正直に管理する**という軸。11社に絞ることで、これが「やろうと思えばできる」規模に収まる。

「毎週更新する」こと自体は差別化にならない（競合silver-choice等も同様の運用を既に実施済み）。差別化になり得るのは、**更新の単位をサービス単位ではなくフィールド単位まで下げ、値と出典を紐付けて管理すること**。これが11社規模でなければ維持不可能な運用密度である、という点に価値がある。

## 2. Target user

既存調査（SEO_CONTENT_FINAL_KW_SERP_AUDIT / SEO_FLOW_RESEARCH）で個人参入可能性A評価・A8案件と自然に接続する4層に絞る。「一人暮らし」「糖質制限」等の需要が大きいテーマは意図的に対象外とする（CV先が現状未提携のnosh/三ツ星ファームが主役のため、後述6章）。

| ユーザー層 | 検索意図の例 | CV先 |
|---|---|---|
| 無添加にこだわる人 | 「無添加 惣菜 宅配」「シェフの無添つくりおき 口コミ」 | シェフの無添つくりおき |
| 減塩が必要な本人 | 「減塩 宅配食 おすすめ」 | 健康直球便／食楽膳 |
| 高齢の家族の食事を探す子世代 | 「高齢者 冷凍弁当 おすすめ」「やわらか食 宅配」 | 食楽膳／健康直球便 |
| 栄養管理をしたい層（要検証） | 「高タンパク 宅配食」 | FIT FOOD HOME |

いずれも「比較検討フェーズで数値の裏取りを求める」層であり、「どれが人気か」ではなく「本当にそうなのか」を確認しに来る。これが本サイトのデータ検証状態表示（12章）と相性が良い理由。

## 3. Competitive positioning

| 軸 | my-best / GYRO等の量産メディア | single-meallife.com / takushoku-repo.com（実食型個人サイト） | 宅食図鑑 |
|---|---|---|---|
| 規模 | 数十〜百社超を浅く網羅 | 40社超をレビュー | **11社に固定** |
| 武器 | 記事量・被リンク | 実食写真・体験 | **フィールド単位の検証状態と出典** |
| 更新運用 | 記事の量産 | 個人の実食ペース | 月次のデータ品質メンテナンス（9章） |
| 個人が模倣困難な資産 | ほぼ無し（誰でも書ける） | 実食コスト（時間・食費） | **「確認済み／未確認／算出値」を偽らず出し続けた蓄積** |

**個人が模倣困難な資産にならないもの**（=差別化にしない）:
- 比較表・送料込み価格・確認日の明記・条件入力シミュレーター → my-best/cachie/silver-choice/kurasimが既に実装済み。標準機能として揃えるだけ（4章）。
- 「更新すること」自体 → silver-choiceが既に毎週更新を実施済み。

## 5. DIFFERENTIATE（現時点で独自価値の根拠がある最小実装）

3章の競合再調査を踏まえ、4つの候補を厳密に評価する。

### ①11社という小規模ポートフォリオ　→ **採用**
根拠: `data/services.json`は既に11社に固定されており、うちA8提携承認済みは5社（シェフの無添つくりおき・食楽膳・ヨシケイ・健康直球便・FIT FOOD HOME）。my-best等は数十〜百社を扱うため個社検証の密度を上げられない。11社なら「価格・送料・解約条件を一次情報で埋め切る」ことが個人運営でも射程に入る規模（現に6/11社で送料confirmed済み）。
**価値分類**: データ資産（高）/ SEO（中、比較の実データが増えるほど有利）/ CV（中）/ 個人運営維持性（高＝これがあるから他の差別化が回る）。

### ②フィールド単位の確認状態　→ **条件付き採用**
現状の`services.json`/`shipping.json`は既に事実上これをprose（notesフィールド）で実現している（例: `shipping.json`のnosh行「送料は地域・食数により変動し単一値ではない」、wellness-dining行「UNCOLLECTED」+理由）。差別化になる条件は、**これをUI上の一貫したステータス表示（CONFIRMED / PENDING_VERIFICATION / UNCOLLECTED / DERIVED）に格上げすること**。単なる内部運用のままではユーザー価値にならない。
**採用条件**: ①各フィールドの表示に「確認済み／確認中／算出値」の可視ラベルを付ける、②「確認中」を欠陥ではなくポリシーとして footer/凡例で説明する。これがなければ単なる社内メモで終わる。
**価値分類**: 信頼（高）/ SEO（低〜中）/ CV（中、「なぜ空欄か」の説明が離脱防止になる）/ 実装コスト（低、既存notesを構造化するだけ）。

### ③値と出典の紐付け　→ **条件付き採用（Phase2、優先度は②の次）**
現状`sources.json`はページに紐付いておらず独立台帳。「この価格はこの出典から」を全フィールドに敷くのは11社×5フィールドでも50件超の紐付けが必要でコストが高い。
**採用条件**: 全フィールドではなく、**A8提携5社の価格・送料・キャンペーンの3フィールドのみ**に絞って出典リンクを表示する（Rule of Three）。未提携6社は据え置き。
**価値分類**: 信頼（中〜高）/ SEO（中、E-E-A-T的な一次情報明記はYMYL隣接ジャンルで評価されやすい）/ CV（低〜中）/ 実装コスト（中）。

### ④「分からない」を正直に表示する設計　→ **②に統合、単独機能にしない**
UNCOLLECTED/PENDING_VERIFICATIONのラベル自体は②の一部として扱う。単独章で「品質表示システム」を作ると過剰設計になる（12章禁止事項に抵触）。ラベルの意味を1箇所（凡例）で説明すれば足りる。

### 採否まとめ

| 候補 | 採否 | 理由 |
|---|---|---|
| ①11社ポートフォリオ | **採用** | 既に実質実装済み。運用密度の前提として維持するだけ |
| ②フィールド単位確認状態 | **採用（最小実装）** | 既存notesの構造化＋UI表示化のみ。新規収集不要 |
| ③値と出典の紐付け | **採用（A8承認5社の3フィールドのみ）** | 全社全項目は過剰。範囲を絞れば低コスト |
| ④正直な「分からない」表示 | ②に統合 | 独立機能化しない |

## 7. Data architecture

### 7.1 現状の評価
`data/services.json` `shipping.json` `campaigns.json` `sources.json`は既にRule of Threeの範囲内にある小さなJSON群であり、汎用DBやCMSは不要。**新しいテーブルやスキーマの追加は行わない**。変更は既存フィールドへの**状態タグの追加**のみ。

### 7.2 最小変更案（実装時の指針。今回はdata/*.json自体は変更しない）

各データ値に付与する状態は4種のみ（5種以上は過剰設計）:

```
CONFIRMED            公式一次情報で確認済み（confirmed_at必須）
PENDING_VERIFICATION 情報はあるが裏取り不十分（例: nosh「492円/食」の宣伝コピー）
UNCOLLECTED          未収集。理由（blocker）を必ず記録する（例: 403 Forbidden, JS描画で取得不可）
DERIVED              一次情報から算出した値（算出式を明記。例: 食宅便690円/食＝4,830円÷7食）
```

これは実は**既にnotesフィールドの文章として運用されている**（shipping.jsonのnosh/wellness-dining/watami-takushoku/mitsuboshi-farm行を参照）。したがって新規に「状態管理システム」を作るのではなく、**既存のnotesの中の状態をstatus専用キー1つとして機械可読にする**だけで十分（例: `"status": "UNCOLLECTED"`を追加、notesは理由説明として残す）。

出典紐付け（5章③）は、A8承認5社の価格・送料・キャンペーンのみ`source_id`（`sources.json`のid参照）を追加する。全項目への拡張はしない。

### 7.3 やらないこと
- 汎用CMS化・管理画面の追加
- verification_blocker用の別テーブル（notesで足りる）
- menus.jsonのスキーマ拡張（現行スキーマで十分。空を埋めるのはデータ収集作業であって設計課題ではない）

### 8.2 修正後の導線

```
検索流入
 ├─ 商標ロングテール記事（無添加つくりおき 口コミ等）─┐
 ├─ テーマページ（高齢者のみ）───────────────┤
 └─ Ranking（一覧比較、SEO最適化はしない）      │

```

### 高齢者テーマの条件付きGO

3軸で評価する: ①個食対応 ②やわらか食対応 ③塩分控えめオプション。

対象候補3社の現状データ充足度:

| サービス | 個食対応 | やわらか食対応 | 塩分控えめ | 現在のデータ状態 |
|---|---|---|---|---|
| 食楽膳 | 明記あり（塩分控えめセット/個食タイプ） | 未確認 | 明記あり | price/campaign/shipping全てCONFIRMED |
| 健康直球便 | 未確認 | 明記あり（やわらか食・消化にやさしい） | 明記あり（減塩） | shipping/campaignはCONFIRMED、priceはPENDING |
| まごころケア食 | 未確認 | 明記あり（やわらか食・ムース食） | 未確認 | **price/shipping/campaign全てUNCOLLECTED** |

**条件付きGOの「条件」**: まごころケア食のUNCOLLECTED項目（特に個食/塩分対応の有無）を最低限埋めない限り、3社中1社が「未確認」のままテーマページを公開することになり、8章のUX監査が既に指摘した「約束と実態のギャップ」問題を再発させる。したがって**高齢者テーマページの公開条件は「まごころケア食の3軸該当有無が公式情報で確認できること」**とする（価格までは不要、対応可否の明記があれば足りる）。

3社確認が揃わない場合は、2社（食楽膳・健康直球便）限定の縮小版として公開するか、Phase2内でPhase3に格下げするかを実データ収集後に判断する。

## 11. Related-service strategy

### 最小設計（採用）
- 最大2〜3件
- タグ一致数が2件以上のサービスのみ表示（1件一致は表示しない＝根拠が弱い）
- 一致するサービスが無い場合はブロック自体を非表示にする（空欄で「関連サービスがありません」と出さない）
- ranking.htmlのCTA階層（詳細ページ内リンク＞公式CTA）と整合させ、関連サービスのリンク先は`/services/{id}.html`（公式CTAへの直リンクにしない＝回遊優先）

### CV/回遊への寄与評価
UX監査（5章）が既に「サービス詳細から類似サービスへの導線が無い」ことを回遊性の主要な欠落として指摘しており、これは4章のMUST MATCH（一般的な比較サイトの標準機能）に相当する。**独自の差別化としてではなく、標準機能の欠落を埋めるものとして実装する**（5章では独自要素として扱わない）。

実装コストは低い（既存の`tags`/`target`フィールドを使った集合演算のみ、新規データ収集不要）。

---

## 12. Data verification strategy

### 12.1 ステータスの意味と表示
7章で定義した4状態（CONFIRMED / PENDING_VERIFICATION / UNCOLLECTED / DERIVED）を、値の隣に短いラベルとして表示する。全ページ共通の凡例（1箇所、フッター付近）で意味を説明する。

### 12.2 UNCOLLECTEDは「たまたま未収集」ではなく理由付きで記録する
既に`shipping.json`で実践済みの運用（例: `watami-takushoku`行「公式サイトへのアクセスが403 Forbiddenで機械取得不可」、`mitsuboshi-farm`行「JavaScript描画のため本文取得不可」）を正式なポリシーとして明文化する。これにより「サボっている」ではなく「取得できない理由が明確」という誠実さを担保する。

### 12.3 出典紐付けの範囲（5章③の実行方針）
A8承認5社（シェフの無添つくりおき・食楽膳・ヨシケイ・健康直球便・FIT FOOD HOME）の価格・送料・キャンペーンの3フィールドに限定して`sources.json`のエントリへリンクする。他6社・他フィールドは据え置き。

## 13. Measurement strategy

「更新すること」自体は差別化にならない（4章冒頭）ため、更新頻度そのものをKPIにしない。計測すべきは以下:

| 指標 | 目的 | 現状 |
|---|---|---|
| GA4流入元×CV | どのテーマ/記事がCVに繋がっているか | 未導入（設計外・定型実装） |
| ページ別直帰率 | 「検索流入→1ページで離脱」の解消度（UX監査5章の問題） | 未計測 |
| 診断ツール完了率 | 診断が「回遊のハブ」として機能しているか | 未計測 |
| CONFIRMED比率（フィールド単位） | 「データで選ぶ」という約束の充足度。11社×主要3フィールド(price/shipping/campaign)のCONFIRMED割合 | 現状: price 3/11、shipping 6/11、campaign 6/11（requires_verification=false基準） |
| 関連サービスのクリック率 | 11章の施策がCV/回遊に実際に寄与するかの検証 | 未計測（実装後に検証） |

GA4導入自体は本設計書の対象外（差別化でも独自設計でもない、定型のインフラ整備）。ただしPhase1の実行条件として並行導入を推奨する。

## 14. Phase roadmap

### Phase 1: MUST MATCHの最低限実装
**実装内容**:
- shipping.jsonの残5社（watami-takushoku, mitsuboshi-farm, wellness-dining, fit-food-home, magokoro-care）の送料/解約条件を一次情報で埋める（アクセス不可の場合はUNCOLLECTED＋理由を維持）
- services.jsonの価格未確認8社のうち、A8承認済み3社（ヨシケイ・健康直球便・FIT FOOD HOME）を優先して価格confirmedへ
- 関連サービスブロックの実装（11章）
- comparisons.jsonのペアをA8承認5社中心に見直す（例: chef-muten-tukuritoki vs syokurakuzen, syokurakuzen vs kenko-chokkyokubin）
- watchlist.jsonにA8承認4社（シェフの無添つくりおき・食楽膳・ヨシケイ・健康直球便）を追加（9章の指摘への対応）

**なぜ必要か**: 「データで選ぶ」という約束と実態のギャップが現時点で最大の弱点（UX監査P0〜P2）。新機能より先にこのギャップを埋めないと、以降のどの差別化施策も土台が無い。

**経済的仮説**: データ充足がCTAの説得力（価値ベースCTA文言の材料）を増やし、CV率を上げる。

**成功指標**: price/shipping/campaignのCONFIRMED比率が11社中8社以上（現状3〜6社）。

**実装しないもの**: 新規テーマページ、診断のprice軸、出典紐付けUI。

**完了条件**: MUST MATCH表（4章）の全項目が「実装済み」になること。

### Phase 2: DIFFERENTIATEの最小実装
**実装内容**:
- フィールド単位ステータス表示（status キー追加＋UI凡例）
- A8承認5社の価格/送料/キャンペーンへの出典リンク
- 高齢者テーマページ（9章の条件＝まごころケア食の3軸確認が前提）
- 診断ツールへのmeal_form軸追加

**なぜ必要か**: MUST MATCHだけでは競合と同水準止まり。3章で評価した「模倣困難な資産」を可視化する段階。

**経済的仮説**: フィールド単位の透明性が信頼を生み、YMYL隣接ジャンルでのE-E-A-T評価・直帰率低下に寄与する（検証はPhase3で計測）。

**成功指標**: 高齢者テーマページ経由のCV発生、関連サービスクリック率>0（測定基盤ができること自体が成功条件）。

**実装しないもの**: 減塩/無添加/高タンパクテーマ、推薦エンジン、全社全項目への出典紐付け。

**完了条件**: 高齢者テーマページ公開＋A8承認5社の出典リンク実装。

### Phase 3: 実測データを見てVALIDATE LATERから追加
**実装内容**（6章の再評価条件を満たした項目から着手）:
- 減塩/無添加/高タンパクテーマ（各再評価条件クリア後）
- 診断のpriceフィルタ（confirmed価格6社以上になってから）
- 実食レビュー（Phase1/2のCVデータを見て投資判断）

**なぜ必要か**: 根拠のない機能追加を避け、Phase1/2で得た実測（CONFIRMED比率・CV・流入）に基づいて次を決める。

**経済的仮説**: 各施策は個別に評価する（本設計書では仮説のみ提示、実装判断はデータ到着後）。

**成功指標**: 各施策の6章記載の再評価条件。

**実装しないもの**: 推薦エンジン・matching DSL（恒久NO-GO、10章）。

**完了条件**: 該当なし（継続的な再評価プロセス）。

## 16. Explicit non-goals（禁止事項）

以下は実装しない。理由も併記する。

| 禁止項目 | 理由 |
|---|---|
| 汎用Themeエンジン | 現在Go判定のテーマは高齢者1つのみ。エンジン化する母数がない |
| matching_rule DSL | 10章でNO-GO確定。11社規模でtags一致以上のロジックは過剰 |
| 高度な推薦エンジン | 同上 |
| 大規模CMS化 | data/*.jsonの規模はCMSを必要としない |
| 汎用UpdateLog基盤 | 「更新」自体は差別化にならない（4章冒頭の設計思想）。更新は内部運用（9章watch.py）に留める |
| 「毎週更新ページ」「月次更新ページ」の新設 | 同上。競合が既に実施済みの標準運用であり独自価値ではない |
| 全社全フィールドへの出典紐付け | コストに見合わない。A8承認5社の主要3フィールドに限定（12章） |
| 汎用API化 | 現状の静的サイト生成（tools/build.py）で要件を満たしており、使われるか不明なAPI層は不要 |
| 減塩/無添加/高タンパクテーマの前倒し実装 | 確認済みデータが不足（6章）。データが揃うまで作らない |
| 診断のpriceフィルタの前倒し実装 | 同上 |
| 実食レビューの前倒し着手 | データ基盤・信頼回復が先（UX監査の結論を踏襲） |

## 17. Final competitive advantage

**宅食図鑑は、大手比較メディアのように100社を浅く並べず、実食型個人サイトのように体験だけで語らない。11社という運営者が実際に検証しきれる範囲に絞り、価格・送料・キャンペーンという主要フィールドを「確認済み／確認中／算出値」のいずれかで正直に開示し、確認できた値には一次情報の出典を紐付ける。この「検証できる範囲だけを、検証した状態のまま見せ続ける」運用密度こそが、個人運営で模倣コストの高い唯一の資産である。**

この定義と矛盾する機能（母数のない一般化、根拠のないテーマ拡張、更新すること自体の演出、確認していない値の断定表示）は、原則として実装対象から外す。
